### 3.3 北京当前温度和风速

用户问题：

> 北京当前温度和风速是多少？

#### 第一次请求

实际回答：

> 大模型服务暂时无法使用，请稍后再试。

耗时：约 `62` 秒

服务日志显示：大模型意图识别请求发生 `APITimeoutError`。

#### 后续请求

天气查询成功，结构化数据如下：

```json
{
  "location": "北京",
  "date": "current",
  "temperature_c": 26.0,
  "weather_description": "小雨",
  "humidity_percent": 51,
  "wind_speed_kmh": 126.0,
  "wind_description": "东北风 5级",
  "precipitation_mm": 1.4,
  "source": "QWeather",
  "timezone": "Asia/Shanghai"
}
```

实际回答：

> 北京（current），小雨，26°C，湿度51%，风速126 km/h，预计降水1.4 mm。

结论：真实天气数据链路可以成功走通，但首次模型超时会造成明显等待。回答中的 `current` 偏内部化；同时出现 `126 km/h` 与 `东北风 5级`，需要确认风速单位换算和展示策略是否符合产品预期。

### 3.15 会话创建、读取和删除

操作顺序：

1. `POST /api/conversations` 创建空会话。
2. `GET /api/conversations/{id}` 读取会话，消息数量为 0。
3. `DELETE /api/conversations/{id}` 删除会话。
4. 再次 `GET /api/conversations/{id}`。

实际结果：

- 创建：HTTP `200`，返回新会话 ID 和“新会话”标题。
- 读取：HTTP `200`，返回空消息列表。
- 删除：HTTP `200`，返回 `{"deleted":true}`。
- 删除后读取：HTTP `404`。

结论：通过。会话生命周期完整，删除后消息也会被级联清理。

## 4. 发现的问题与建议

### P1：大模型超时等待过长

北京当前天气第一次请求等待约 62 秒，最终返回“ 大模型服务暂时无法使用，请稍后再试。 ”。这会明显影响用户对系统可用性的判断。

建议：

- 将模型连接和读取超时控制在更短范围。
- 意图识别超时后尽快回退到规则解析和天气查询。
- 在响应中明确标识“已使用规则回答”或返回可区分的降级状态。

### P2：HTTP 200 包含模型错误

模型超时时接口仍返回 HTTP 200，虽然响应体的 `status` 是 `error`，但监控、前端和用户都不容易区分服务错误与正常回答。

建议：保留业务状态字段的同时，评估对不可用错误返回更明确的 HTTP 状态，或在前端针对 `status=error` 提供重试按钮。

### P2：内部字段出现在用户回答中

回答中的 `北京（current）` 不如“北京当前天气”自然。

建议：格式化回答时将 `current` 转换为“当前”，将 `today` 转换为“今天”。

### P2：风速展示需要确认单位

当前同时显示 `风速126 km/h` 和 `东北风 5级`。需要确认 API 字段的单位换算是否正确，以及普通用户是否更适合看到风级、米/秒或公里/小时。

### P3：前端不渲染 Markdown

连续追问回答中的 `**51%**` 会原样显示星号。

建议：如果产品需要 Markdown 效果，增加安全的 Markdown 渲染；否则在模型提示词中要求返回纯文本。

## 5. 验收结论

天气查询、预报、景点建议、普通大模型聊天、混合会话、会话持久化、连续追问和异常提示等核心流程均已手工验证。普通聊天路由和历史上下文验证通过，但真实模型仍存在 40～70 秒级超时风险；正式提升用户体验时，优先处理大模型超时和降级速度，其次优化内部字段及风速展示。
