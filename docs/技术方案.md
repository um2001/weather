# 天气助手 Agent 技术方案

## 1. 方案目标

本方案用于实现天气助手 Agent 的第一阶段 MVP，验证以下闭环：

```text
自然语言输入 → 查询意图与参数提取 → 天气工具调用 → 数据标准化 → 中文回答
```

方案重点是保持实现简单、行为可测试，并让天气服务与模型逻辑解耦，为后续增加数据源和 HTTP 接口保留清晰边界。

## 2. 技术选型

| 领域 | 选型 | 说明 |
| --- | --- | --- |
| 运行时 | Python 3.11+ | LLM、HTTP 和测试生态成熟 |
| LLM 编排 | `langchain-core` | 工具定义、消息和结构化输出；避免引入不必要的完整生态 |
| 模型适配 | `langchain-openai` | 接入 OpenAI 或兼容 OpenAI API 的模型，后续可替换适配包 |
| 数据模型 | Pydantic | 定义查询参数、标准天气数据和错误边界 |
| HTTP 客户端 | httpx | 调用 wttr.in，提供超时和可测试的请求接口 |
| CLI | Typer + Rich（可选） | 实现命令行交互和友好输出 |
| 测试 | pytest + respx | 对业务逻辑和天气 HTTP 请求进行自动化测试 |
| 依赖管理 | uv | 管理虚拟环境和依赖，简化本地开发 |
| 日志 | Python `logging` | 记录请求、工具调用和异常，不记录敏感信息 |
| 调试追踪 | LangSmith（可选） | 开发调试阶段观察模型和工具调用链 |

第一版不引入向量数据库、复杂记忆、多 Agent 或 LangGraph。当前只有一个天气工具，直接使用受控流程更容易验证和测试。

## 3. 总体架构

```text
┌──────────────┐
│ CLI 交互层   │
└──────┬───────┘
       │ 用户问题 / 中文回答
┌──────▼───────┐
│ Agent 协调层 │ 结构化提取、流程控制、回答生成
└──────┬───────┘
       │ WeatherQuery
┌──────▼───────┐
│ 天气服务层   │ get_weather + WeatherProvider
└──────┬───────┘
       │ 标准化 WeatherData
┌──────▼───────┐
│ wttr.in      │ 外部天气服务
└──────────────┘
```

Agent 协调层不允许在没有天气数据时生成实时天气结论。模型可以负责识别意图和组织语言，程序负责参数校验、工具执行和错误边界。

## 4. 核心流程

### 4.1 正常查询

1. CLI 接收用户输入。
2. 模型将输入转换为 `WeatherQuery`，包含地点、日期和所需指标。
3. 程序校验地点是否存在、日期是否在 MVP 支持范围内。
4. 调用 `get_weather`。
5. `WttrProvider` 请求 wttr.in，并转换为 `WeatherData`。
6. 模型只能基于 `WeatherData` 生成中文回答。
7. CLI 输出回答，并继续等待下一次输入。

### 4.2 缺少地点

如果模型识别出天气意图但没有地点，程序不调用天气服务，直接询问用户补充城市或地区。

### 4.3 服务失败

超时、非成功响应、响应格式异常或无法解析时，天气服务层返回明确的领域错误。协调层向用户说明暂时无法查询，不向模型提供可被误读为真实天气的数据。

## 5. 模块边界

建议的代码结构如下，具体文件名可以在实现阶段微调：

```text
src/weather_agent/
├── cli.py                 # 命令行入口
├── agent.py               # 模型调用和受控流程
├── schemas.py             # WeatherQuery、WeatherData 等 Pydantic 模型
├── tools.py               # get_weather 工具定义
├── providers/
│   ├── base.py            # WeatherProvider 协议或抽象接口
│   └── wttr.py            # wttr.in 适配器
└── errors.py              # 领域错误和用户可见错误映射

tests/
├── test_schemas.py
├── test_provider_wttr.py
├── test_tools.py
└── test_agent_flow.py
```

关键边界：

- `providers` 只负责外部天气服务请求和响应转换。
- `tools` 只暴露稳定的 `get_weather` 接口，不泄漏 wttr.in 的响应格式。
- `agent` 只依赖标准化数据，不依赖具体天气供应商。
- `cli` 不包含天气解析和模型编排细节。

## 6. 核心数据结构

### 6.1 查询参数 `WeatherQuery`

- `location: str`：城市或地区名称，必填。
- `date: str`：MVP 支持 `current` 或 `today`。
- `unit: str`：默认 `celsius`，暂不开放复杂单位切换。
- `metrics: list[str]`：可选指标，如温度、天气状况、湿度、风速、降雨概率。

### 6.2 标准天气数据 `WeatherData`

- `location`
- `date`
- `temperature_c`
- `weather_description`
- `humidity_percent`
- `wind_speed_kmh`
- `precipitation_probability_percent`
- `source`

字段允许为空时，回答中应省略该指标，而不是填入猜测值。外部字段缺失属于正常数据差异，无法解析核心字段则视为服务异常。

## 7. LangChain 使用范围

LangChain 主要用于三件事：

1. 将 `WeatherQuery` 作为结构化输出模型，减少手工解析 JSON。
2. 将 `get_weather` 暴露为模型可调用工具。
3. 统一消息、模型适配和调试追踪接口。

建议先使用单次结构化调用加程序控制的工具执行。如果后续出现多个工具、复杂分支、重试或可恢复状态，再评估迁移到 LangGraph；不要为了使用框架而提前引入状态图。

## 8. 配置与运行

环境变量建议包括：

```text
LLM_API_KEY=...
LLM_MODEL=...
LLM_BASE_URL=...        # 使用兼容 API 的模型时配置
WEATHER_TIMEOUT_SECONDS=8
LOG_LEVEL=INFO
```

密钥只从环境变量或本地未提交的配置文件读取，不写入代码和日志。天气服务地址作为 provider 的配置项管理，便于后续替换。

## 9. 异常处理与可靠性

- 所有外部请求设置明确连接和读取超时。
- 对网络错误、非 2xx 响应和格式解析错误分别记录日志。
- 对用户隐藏底层堆栈，只返回简洁、可行动的中文提示。
- 天气服务失败时禁止生成没有数据依据的天气结论。
- MVP 暂不实现复杂重试；如需重试，优先只对短暂网络错误做一次有限重试。
- 通过日志记录请求耗时、provider 和错误类型，避免记录 API Key。

## 10. 测试方案

测试不依赖真实天气网络：

- `test_schemas.py`：验证必填字段、默认日期和单位。
- `test_provider_wttr.py`：使用 `respx` mock 正常响应、超时、非 2xx 和异常 JSON。
- `test_tools.py`：验证工具返回统一的 `WeatherData`，不泄漏 provider 原始格式。
- `test_agent_flow.py`：验证天气查询调用工具、缺少地点时澄清、服务失败时不编造回答。
- CLI 集成测试：验证输入、输出和退出行为。

验收时至少覆盖产品设计文档中的四项标准，并在提交前执行完整 pytest 测试集。

## 11. 实施阶段

### 阶段一：项目骨架

建立 uv 项目、配置环境变量、CLI 入口、Pydantic 模型和基础日志。

### 阶段二：天气适配器

实现 wttr.in 请求、超时处理、响应解析和标准化数据模型，并完成 provider 测试。

### 阶段三：模型与受控 Agent 流程

加入结构化查询提取、`get_weather` 工具和基于工具结果的中文回答。

### 阶段四：验收与可观测性

补齐异常场景、CLI 测试、日志字段和可选 LangSmith 调试配置。

## 12. 后续演进

- 增加 Open-Meteo provider，并在 provider 层实现可配置的备用数据源。
- 支持地理编码、时区和未来 3～7 天预报。
- 增加短时缓存，降低重复请求和外部服务压力。
- 在保持核心服务接口不变的情况下增加 HTTP API 和 Web UI。
- 当流程出现多工具、多分支或长状态后，再引入 LangGraph。

## 13. 当前待确认事项

- 选用哪一家 LLM 服务及其模型名称。
- 是否要求完全离线兼容的本地模型。
- wttr.in 在目标部署环境中的可访问性和稳定性。
- CLI 之后是否直接提供 HTTP API，还是先验证更多天气能力。
